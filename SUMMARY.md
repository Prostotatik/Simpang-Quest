# Simpang Quest — prototype summary

An interactive fantasy-map trip planner for a group of travellers in Peninsular
Malaysia. The UI is built 1:1 against `assets/design_reference.png`; the map art
is `assets/map.png`.

```
npm install
npm run dev      # http://localhost:5273
npm run build    # type-check + production bundle
```

The Google Maps key lives in `.env` as `VITE_GOOGLE_MAPS_API_KEY`.

---

## What is real

| Area | Status |
|---|---|
| Google Maps JS API | **Real.** A live `google.maps.Map` — real pan, zoom, projection, restriction. |
| Map art | **Real overlay.** `public/map.jpg` is drawn as a `GroundOverlay` pinned to real lat/lng bounds. Default tiles are styled away. |
| Coordinates | **Real.** Every POI carries its true latitude/longitude; markers land on the art where the place actually is. |
| Planning engine | **Real, rule-based.** Scoring, filtering, budgeting, reach from the start location, day-splitting and nearest-neighbour routing all run on the live party/trip state. |
| Distances | **Real.** Haversine over the real coordinates (used for scoring, ordering and the Forces Majeure radius). |
| Drawn trails | **Real roads.** Gold and grey trails follow driving geometry from the Directions service, redrawn with the custom dashes. Legs the service can't answer (islands, ferry hops) fall back to a deterministic bowed trail. |
| Travel modes | **Decided per leg, not measured.** `src/engine/modePlan.ts` is the mock stand-in for the agent's routing call: an explicit table of named pairs plus a short fallback. Sea and air crossings are fixed by geography. Nothing downstream re-derives a mode from geometry. |
| Every control | **Real.** Party, character sheets, journal statuses, itinerary add/remove, Forces Majeure — all mutate the store and force a recompute. |
| Trip terms | **Derived, never typed.** Dates, origin, radius, duration and budget fall out of the party sheets (`engine/deriveTrip.ts`). The Trip panel is read-only; its "Why" dialog shows where each figure came from and links back to the traveller behind it. |
| Side panels | **Real scrolls.** Party, Trip Details and Quest Journal each roll up and down on their wooden rods; state lives in the store. |
| Node card | **Anchored to its node.** Clicking a marker, a candidate card or a journal row unfurls the detail sheet out of that node with a tether, and flips corner depending on free space. Forces Majeure opens inside the same card. |

## What is mocked

| Area | How |
|---|---|
| Backend | None. Everything lives in a Zustand store in memory; a page reload resets to the seed data. |
| LLM / AI | None. Zero AI calls. The "Orchestrator" is a scripted reasoning ticker plus the rule engine in `src/engine/`. Every seam an agent will own is marked `PROTOTYPE:` in the source — `deriveTrip.ts`, `modePlan.ts`, `route.ts`, `scoring.ts` (weather) and `REASONING_STEPS`. |
| POI dataset | 35 hand-written entries in `src/data/pois.ts`. Real names and coordinates, invented costs/durations/tags. No runtime geocoding, so the demo never depends on network or quota. |
| Photography | `public/poi/*.jpg` are procedurally painted vignettes generated by `scripts/gen-poi-art.py` — one per POI, deterministic, offline. |
| Party portraits | CSS medallions (monogram on a painted ground), not photographs. |
| Weather | `weatherOk()` — a deterministic hash of the POI id, so the "good weather forecast" line never flickers between renders. |
| Journal progress | The first stops are seeded Completed / In Progress so the board reads like a trip in flight. Clicking a status pill cycles it manually; there is no GPS or calendar behind it. |
| Scouting animation | A scripted reveal: nodes appear one at a time as a grey `?`, then resolve into their final icon, and each leg inks itself in dash by dash (`useDrawnPaths`). It imitates an agent exploring; underneath it is `setTimeout` and a rAF loop. |

## Map calibration

The raw art is a portrait plate of the peninsula. `scripts/gen-map.py` pads it
with painted ocean so a 16:9 viewport is filled, grades the sea to the deep teal
of the reference, adds mist and a vignette, and writes `public/map.jpg`.

The pixel→degree fit (least squares over George Town, Kuala Lumpur, Johor Bahru,
Kota Bharu, Tioman, Melaka, Ipoh, Kuantan, Alor Setar and Singapore) is:

```
lng = 0.0046524099 * x + 99.5696397
lat = 7.1529428 - 0.0043799807 * y
```

which gives the overlay bounds used in `MapCanvas.tsx`:

```
north 7.1529   south 1.0472   west 96.3595   east 108.0277
```

Residuals are under ~0.15°, which is well inside the accuracy of the artwork
itself. The map is locked to those bounds (`restriction` + `strictBounds`) with
`minZoom: 8` / `maxZoom: 10`, no tilt, no rotation, and every default control
and POI label disabled, so only the art and the custom overlay are visible.

## The rule engine

`src/engine/scoring.ts` builds a party profile (interest weights, vegan/
accessibility flags, the tightest personal budget and adventure length, the
count of shared free days) and scores each POI against it:

* **reach** — great-circle distance from the party's start location; past `maxTravelKm` the place is ruled out entirely, and closer places score higher
* **tag overlap** with the party's interests — the main positive signal
* **budget** — `costRM` against the per-head share; over budget is a hard block
* **duration** — against the shortest `maxAdventureHours` and the longest free window
* **free dates** — at least one day where half the party is free
* **diet** — a non-vegan-only food stop is blocked when anyone in the party is vegan
* **accessibility** — a POI without step-free access is blocked when anyone needs it
* **weather** — the mocked deterministic forecast

Every POI ends up in one of four buckets, and the map shows all of them:

| Bucket | On the map |
|---|---|
| kept | gold `!` (tavern for food, tent for a booked stay), joined by the gold dashed route |
| candidate | gold `?` — viable, waiting for a decision |
| scouted, passed | grey `?` — walked to, didn't make the cut |
| not suitable | grey `!` — blocked by a hard rule |
| bed for the night | gold tent — a `stay` POI the planner books, never scored |
| airport / ferry terminal | blue-ringed disc with the fare — where a crossing really starts |

Stops that sit on top of each other are fanned out around their cluster centre.
Clustering is single-link and measured in **screen pixels at the live zoom**, then
a relaxation pass pushes apart anything still closer than one marker width and
clamps each node within 96 px of its true position — so every node stays clickable
and captions flip to the side the node was fanned towards.

`src/engine/route.ts` takes the top scorers while the shared budget holds (with a
soft cap of three stops per region), orders them with a greedy nearest-neighbour
walk that **starts at the party's base** and is then 2-opted as a closed loop, and
slices that walk into days. The route leaves the base-camp flag and comes home to
it. When a day ends more than 70 km out and another day follows, the nearest
affordable hotel is booked into the plan.

It then lays out the **scouting trails**: every stop (and the base) sends two or
three grey dashed probes to the nearest places that were scouted and set aside,
so each node visibly has one gold way onward and a handful of rejected ones.

Every hop is its own leg with its own **travel mode**. That mode is a decision,
not a calculation: in production an agent picks it per leg, and until then
`src/engine/modePlan.ts` stands in with an explicit table (`base|penang-streetfood`
is a train, `kl-petronas|jalan-alor` is a walk) and a short fallback for anything
unlisted. Hub approaches are always road transfers, and crossings are pinned by
`CROSSING_MODE` so a stretch of open water can never come out labelled as a train.
The glyph is
drawn pointing "up" and rides the polyline as a symbol, so Google rotates it onto
the edge it sits on and it always faces the way the party is going. Short legs get
one glyph at the midpoint; long ones repeat every 150 px.

Hubs are chosen as a **pair**, by the cost of the whole drive + crossing + drive.
Picking the nearest hub to each end separately sends a Cherating → Tioman ferry
out of Merang, 330 km up the coast; scoring the complete journey keeps it at
Mersing. A probe is only treated as drivable when **both** of its ends are on the
mainland, so a trail leaving an island is always a crossing.

Both the gold route and the grey probes are drawn along **real driving geometry**
(`src/engine/directions.ts`): each leg is requested once, cached for the session,
serialised so the service is never hammered, and replaced by a curved trail when
the answer is ZERO_RESULTS — which is what happens for Tioman, Redang and
Langkawi, where the real trip is a ferry anyway.

Every reason shown under **Why it's a good fit** is the engine's own output, not
static copy — negative reasons render with a red cross.

Edits to the party or the trip re-run the whole pipeline after a 700 ms debounce,
and **Regenerate** runs it immediately. Change the budget, drop a vegan tag, add an
accessibility need, move the base to Penang or pull the radius down to 150 km and
the node set on the map genuinely changes — a short radius produces a tight local
trip instead of a march across the whole peninsula.

**Forces Majeure**: the cloud button on a confirmed node marks that stop closed,
then searches the dataset for the nearest POI that shares tags, fits the budget and
sits within a sensible radius — and **swaps it in by itself**, re-running the loop
ordering so the golden route is rebuilt around the replacement. The card keeps an
*Undo* next to *Keep it*.

## Project layout

```
src/
  data/pois.ts          35 Malaysian POIs (real coordinates)
  data/seed.ts          seed party + trip
  data/startLocations.ts  ten real hubs the party can set out from
  engine/deriveTrip.ts  trip terms worked out from the party sheets
  engine/scoring.ts     party profile + per-POI scoring
  engine/route.ts       itinerary assembly, day split, scout trails, alternatives
  engine/directions.ts  road geometry with a bowed fallback
  engine/travel.ts      the directional glyphs + the fixed crossing modes
  engine/modePlan.ts    mock of the agent's per-leg transport decision
  engine/legs.ts        splits sea/air hops through the nearest hub, with fares
  data/hubs.ts          airports and ferry terminals + the fare model
  store/useStore.ts     single Zustand store (party, trip, plan, UI state)
  components/
    MapCanvas.tsx       live map, ground overlay, route + scout polylines, markers
    ScrollPanel.tsx     the roll-up parchment scroll used by the side panels
    useDrawnPaths.ts    stroke-on progress so routes draw rather than snap
    MapMarker.tsx       SVG node icons (?/!/tavern/camp) + storm button
    NodeCard.tsx        the detail sheet that unfurls out of a node
    PartyPanel.tsx      TripPanel.tsx  Orchestrator.tsx
    QuestJournal.tsx    stops grouped by day, sized against its column
    CandidateStrip.tsx  collapsible scouting rail
    Legend.tsx
    Onboarding.tsx      Modals.tsx
scripts/
  gen-map.py            builds public/map.jpg from the raw art
  gen-poi-art.py        builds public/poi/*.jpg
  shot.mjs              headless screenshot harness used while building
```

The HUD is composed against a 1560×900 stage and zoomed down on smaller windows,
so the layout never reflows out of the reference composition while the live map
underneath keeps its full size.

It reads as three rails around the map. **Left** is the input the planner acts on
— party, trip terms, and the orchestrator that drives them, at one width, with the
panels scrolling if they outgrow the column. **Right** is the output — the journal
takes all the slack it can, and the legend sits under it as a collapsed key,
opening into two columns when asked. **Bottom** is optional extra: the scouting
rail, centred between the rails and collapsible to a sliver.

## Wiring a real backend later

1. **Places.** Replace `POIS` with a fetch. `Poi` is the only shape the engine
   knows about, so a `GET /pois?bbox=…` returning the same fields is a drop-in.
   Real photos replace `public/poi/<id>.jpg` by changing the one `src` in
   `PoiImage`.
2. **Persistence.** The store is a single Zustand slice. Persisting a trip means
   POSTing `{ members, trip, itinerary }` on change and hydrating it at startup;
   nothing else in the UI reads state from anywhere else.
3. **Deriving the trip.** `deriveTrip(members, previous)` is the first thing an
   agent should take over: it already receives the whole party and returns the
   complete `Trip`, so swapping the arithmetic for a model call changes nothing
   else. Each rule inside is commented with what it stands in for.
4. **Real planning.** `planTrip()` is a pure function of
   `(scored, members, trip)`. Swap its body for a server call — or for an LLM —
   as long as it still returns `{ itinerary, candidates, rejected }`. The
   Orchestrator's reasoning ticker is already shaped to stream real tokens:
   replace `REASONING_STEPS` with a stream and drive `reasoningStep` from it.
5. **Weather / closures.** `weatherOk()` and `triggerForceMajeure()` are the two
   seams where a real forecast API and a real "temporarily closed" signal would
   land; both already flow into scoring and into the UI.
6. **Live tracking.** `JournalStatus` is currently user-toggled. A real build
   would derive it from geolocation plus the planned day, using the same
   `setStatus` action.
